# Архитектура 0.3.0rc2

## Цель и граница универсальности

Общая схема производства программно создаваемого видео сохранена: сценарий, аудио, временная разметка, визуальный план, монтаж. RC реализует **фиксированный audio-first workflow**, а не произвольный DAG и не систему для любого YouTube-жанра.

```text
Recipe.script_prompt ──→ TextProvider ──→ Script
                                            │
                                            ▼
                                       AudioProvider
                                            │
                              task ID → Candidate[1..16]
                                            │ для каждого кандидата
                                            ▼
                                  audio file + AlignmentRequest
                                            │
                                   TimestampProvider
                                            │
                                        Transcript
                                            │
                  Recipe.timeline + семантическая проверка
                                            │
                            TextProvider → VisualPlan
                                            │
                              Recipe.compile_plan
                                            │
                              общий ScenePlan v2
                                            │
                    структурная проверка → Renderer → MP4
```

Планирование визуала выбирает объекты, фон и цвет; **не доверяем LLM расчёт длительностей или координат**. Таймлайн и компоновку вычисляет Recipe. Renderer воспринимает только фон и набор `TextLayer` / `ImageLayer`.

## Контракты

`Script` состоит из сегментов с произвольным безопасным `id`, текстом, необязательным asset ID и аудиоподсказкой. `INTRO`, `A` или `10` — соглашения конкретного Recipe, не языка core.

`Transcript` — нормализованные интервалы `text/start/end`, указание провайдера и гранулярности. Поля `alignedWords`, `startS`, `endS` стороннего SunoAPI обрабатываются только в адаптере. Отдельный aligner можно заменить без изменения ScenePlan или renderer.

`VisualPlan` связывает ID сегмента с выбранными ассетами. `ScenePlan(version=2)` содержит абсолютные интервалы сцен, background ID и ограниченные типизированные слои. Координаты нормализованы, неизвестные поля/типы и недопустимые размеры отвергаются. Никакого исполняемого Python, пути к произвольной функции или команды оболочки в плане нет.

В каталоге `kind=character` — сохранённое имя foreground-ассета; это может быть яблоко, геометрический объект или другая картинка, не обязательно персонаж. Пути разрешаются через каталог, проверяются на выход за его корень, включая symlink. LLM получает описания и logical IDs, а не локальные пути.

## Кто за что отвечает

`recipes/` содержит prompts, правила сценария, семантическую проверку транскрипции, построение таймлайна и слоями выраженную компоновку. `providers/` содержит адаптеры текста, музыки и выравнивания. `providers/factory.py` — явная точка сборки приложений, а не автоматический загрузчик плагинов из YAML.

`pipeline/orchestrator.py` управляет стадиями и сохранением результатов. `pipeline/timeline.py` и `validation.py` содержат общие временные/структурные проверки. `rendering/renderer.py` реализует CPU-композицию RGBA кадров и MoviePy/FFmpeg кодирование. `tasks.py` — тонкие адаптеры очереди над теми же методами Pipeline.

В local mode ветки проходят последовательно. В queue mode подготовка может идти параллельно, а rendering по умолчанию ограничен одним процессом/потоком и файловой блокировкой на общий output-root. Это single-host/shared-filesystem модель, не распределённый сервис с транзакционной БД.

## Восстановление и защита расходов

Перед отправкой аудио создаётся атомарный маркер `submitting`. Потеря ответа или остановка процесса после этого не даёт автоматически отправить запрос повторно. Владелец сверяет кабинет и использует `attach-task`. Источник истины об оплате — поставщик, не локальный статус.

Для выравнивания сохраняется отдельная попытка. У billable-провайдера потерянный результат требует явного `--retry-alignment --allow-paid`. Повторять такой retry через очередь запрещено. Текстовые LLM-стадии не получают автоматически повторных SDK-попыток, но их повтор после аварии до сохранения не является exactly-once: бюджет всех провайдеров системой не гарантируется.

Каждый кандидат имеет отдельный `branch.json`; плохой кандидат не блокирует хороший. Ошибки качества не запускают автоматическую платную регенерацию. Сохранённый артефакт может быть переиспользован после проверки его контракта и хэшей.

Снимки config/recipe/catalog/ассетов контролируются хэшами; script после отправки также защищён от случайных изменений. До повторного использования MP4 проверяются входные артефакты и его SHA-256, а не только наличие файла. После кодирования FFmpeg декодирует весь результат. Временный файл заменяет `final.mp4` только после успешной проверки.

Хэши и файловые locks защищают от случайного изменения/конкурирующих запусков в доверенной локальной среде. Это **не подписи против злонамеренного пользователя**, не гарантия работы на NFS и не полная защита при аппаратной потере питания.

## Что означает validation passed

Для alphabet проверяем явные маркеры `A is for ...`, порядок, покрытие выбранных букв и соответствие предметов. Для counting проверяем числовой якорь, нужный объект/форму слова и количество слоёв в результирующем плане. Обе текущие Recipe требуют различимых границ сцен и финального текстового якоря.

Это строгие форматные эвристики, а не ASR-оценка качества. Повторы припевов, необычные формулировки, склейка слов, неточная транскрипция могут приводить к отказу даже для приемлемой песни. Само наличие слова в данных поставщика не доказывает его наличие в звуке. Поэтому `validation.json` явно сохраняет `acoustic_correctness_checked=false`.

## Сознательно отсутствует

Нет LLM-агентов, self-repair, публикации на YouTube, TTS/Whisper-адаптера RC, веб-интерфейса, распределённого планировщика, произвольных видеослоёв с камерой/переходами, автоматической модерации, гарантированного контроля бюджета и acoustic evaluation. Эти направления не скрыты за интерфейсами как будто уже реализованные функции.

## Особенности реализации

`SubmissionRejected` — явный контракт адаптера. Неожиданные исключения submit оставляют `submission_uncertain`, а не открывают повтор. Прогресс рендера читается из файла, поэтому отказ консоли не заполняет pipe дочернего процесса. Бюджеты кэша относятся к удерживаемым масштабированным изображениям, не ко всей RAM. Незакрытый долг Pillow описан в `SECURITY_AND_ASSETS.md`.

В актуальном AlphabetRecipe цвет основных букв берётся из палитры, а компоновка/интро — из детерминированного RNG по сохранённым таймингам. Gemini по-прежнему выбирает фон и asset ID; цвета intro/outro берутся из VisualPlan.
