# Производственный pipeline: от идеи до MP4

[← Главный README](../README.md) · [Архитектура кода](ARCHITECTURE.md)

## Что здесь называется «блоком»

В этом документе **блок** — этап производства ролика, а не обязательно одна папка Python. Например, `Recipe` участвует и в создании сценария, и в определении таймингов, и в размещении элементов. `Pipeline` управляет всеми блоками, не являясь отдельной стадией художественной генерации.

```text
                  Recipe: правила формата
                      |       |        |
                      v       v        v
Вход/Config ──> Script ──> Audio ──> Transcript/Timing
                |                       |
                |                       v
                +─────────────────> VisualPlan
                                        |
                                        v
                               Recipe.compile_plan
                                        |
                                        v
                                    ScenePlan
                                        |
                                        v
                          Pillow / MoviePy / FFmpeg
                                        |
                                        v
                                    final.mp4

JobStore: состояния, snapshots, checkpoints, branches
Pipeline: порядок этапов, ошибки, восстановление
```

## Где проходят границы

| Этап | Вход | Выход | Реализованный компонент |
|---|---|---|---|
| Сценарий | Recipe + каталог + настройки | `Script` | `Recipe.script_prompt`, `TextProvider` |
| Аудио | `Script` + audio config | `Candidate` и файл аудио | `AudioProvider` |
| Синхронизация | Сценарий + кандидат + аудио | `Transcript`, `Timing`, `SRT` | `TimestampProvider`, `Recipe.timeline` |
| Визуал | Каталог + сценарий + транскрипция | `VisualPlan` | `TextProvider`, `Recipe.visual_prompt` |
| Сборка сцен | `VisualPlan` + тайминги + Recipe | `ScenePlan` | `Recipe.compile_plan` |
| Рендер | `ScenePlan` + аудио + SRT + ассеты | `final.mp4` | `rendering/` |

## Как выглядит один job

Новый job создаёт отдельный каталог `output/<uuid>/`. Там хранятся снимок конфигурации и общие данные. У каждого полученного аудиокандидата есть ветка `v0`, `v1` и так далее.

```text
output/<job-id>/
├── job.json
├── config.json
├── script.json
├── v0/
│   ├── branch.json
│   ├── audio.mp3              # В live-режиме; в demo может быть WAV
│   ├── transcript.json
│   ├── timing.json
│   ├── visuals.json
│   ├── scene_plan.json
│   ├── subtitles.srt
│   ├── final.mp4
│   └── render_result.json
└── v1/
    └── ... собственные материалы второго кандидата
```

Это **схема типичного завершённого job**, не полный список всех файлов и служебных markers. Ветви могут завершаться разными статусами. Каждый новый `demo`/`run` создаёт новую папку.

## Почему сохранение промежуточных результатов принципиально

1. Неудачный рендер не должен приводить к повторной оплате песни.
2. Один повреждённый кандидат не должен обязательно останавливать все остальные.
3. Повторяемый `ScenePlan` позволяет менять визуальные правила отдельно от платных провайдеров.
4. Можно различить «поставщик точно отказал» и «запрос мог пройти, но ответ не получен».

Проект не обещает абсолютную гарантию exactly-once на стороне внешних API. Если результат платной отправки неизвестен, система сохраняет это состояние и требует ручной проверки.

## Как управлять изменениями

Меняешь слова и структуру обучения — работаешь со **сценарием/Recipe**. Меняешь источник музыки — с **AudioProvider**. Хочешь другую модель выравнивания — с **TimestampProvider**. Переставить буквы и персонажей, поменять размер и цвет — с **Recipe.compile_plan**. Ускорить GIF — с **renderer**, не с Gemini.

Внутри существующего job нельзя произвольно менять сохранённый snapshot или входные checkpoint'ы. Для нового полного варианта создаётся новый job; для повторной сборки по сохранённым результатам применяется `replay`.
