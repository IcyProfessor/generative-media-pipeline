# Расширение без изменения core

## Новый формат

Минимальный контракт описан в `src/genmedia/recipes/base.py`. Новый Recipe задаёт имя/версию и реализует:

| Метод | Ответственность |
|---|---|
| `validate_catalog` | Достаточность локальных ресурсов до обращения к API |
| `script_prompt`, `fixture_script` | Запрос реального сценария и детерминированный offline пример |
| `validate_script` | Собственные семантические ограничения |
| `timeline` | Границы сцен из нормализованной транскрипции |
| `visual_prompt`, `fixture_visuals` | Запрос выбора визуала и fixture-аналог |
| `compile_plan` | Превращение семантики формата в общий ScenePlan |

Для подключения нужна регистрация в `recipes/__init__.py` через `register_recipe`, либо передача реализации при создании job/Pipeline. В многопроцессном режиме регистрацию нужно выполнять и в worker-приложении; произвольные import-пути из конфигурации не исполняются. CLI `--recipe` перечисляет встроенные форматы; для нового зарегистрированного формата используйте YAML/свою точку входа.

Практический полный пример — **`tests/test_extensibility.py`**. Его test-only Recipe использует `chapter_one`/`chapter_two`, без INTRO/OUTRO, букв или чисел. Он проходит тот же Pipeline и настоящий subprocess renderer. Это доказательство отсутствия доменных предположений, **не третья готовая публичная функция** и не narrated explainer с реальным TTS.

`CountingRecipe` демонстрирует, где должно жить правило N объектов: именно компилятор Recipe создаёт N `ImageLayer`, а не renderer. Для другой компоновки меняйте Recipe, не условие `if recipe == ...` в backend.

## Новый провайдер

Порты находятся в `providers/base.py`. Текстовый адаптер получает `Prompt` и целевую Pydantic-схему, возвращает объект этой схемы; аудио-адаптер реализует preflight, submit, poll и download; aligner возвращает только `Transcript`. `AlignmentRequest` передаёт уже сохранённое аудио, исходный сценарий и task/candidate metadata: локальный aligner может игнорировать удалённые ID.

Провайдер не должен знать буквы, число копий объекта или имена Recipe. Преобразование специфичных API-полей в общий контракт выполняется **внутри адаптера**, как в `providers/suno_schema.py`.

Подключение через конфигурацию требует явного добавления разрешённого имени и фабрики в `providers/factory.py`. Это небольшой composition root; `Pipeline` при этом менять не требуется. Для unit/integration теста можно инжектировать объект в `Pipeline(..., text_provider=..., audio_provider=..., timestamp_provider=...)`; при нестандартных именах конфигурации их также нужно разрешить в factory.

Контракт смены провайдера означает одинаковый тип результата, **не одинаковые возможности или качество**. Другой music/TTS provider может возвращать одного кандидата вместо двух, не иметь встроенных timestamps, требовать другой стиль текста или иной aligner. Эти ограничения нужно проверить отдельно. FixtureAlignment намеренно не разрешён поверх реального аудио.

## Другой renderer

`RenderRunner(job, branch, timeout)` — граница оркестратора. Текущий subprocess backend получает ScenePlan, каталог, аудио и SRT. Альтернативный runner может интерпретировать те же поддерживаемые слои, но должен создать валидный MP4; ядро отдельно проверит результат.

`rendering/runner.py` не загружает Recipe: уже скомпилированный ScenePlan самодостаточен относительно каталога/аудио. Для новых **типов** слоёв потребуется новая версия IR и обновление backend. Обещания, что любой формат можно добавить одним prompt, в RC нет.

## Версии и тесты

При изменении смысловых правил увеличивайте `Recipe.version`. Старый job с другой версией не возобновляется молча. При изменении схемы меняйте её версию и пишите явную миграцию в новый job.

Для каждого расширения нужны fixture happy path, плохой сценарий, плохая разметка, offline replay без API и короткий настоящий рендер. Изменение внешнего API дополнительно проверяется mock HTTP и отдельным opt-in live smoke с ограниченным бюджетом.
