# Этап 01. Создание сценария

[← Все этапы](../PIPELINE.md) · [Далее: аудио →](02-audio.md)

## Почему этот этап выделен отдельно

У генеративной модели нет обязанности писать именно тот текст, который ожидает видеомонтаж. Она может перепутать порядок букв, придумать объект, отсутствующий среди GIF, или вывести обычный абзац вместо JSON. Пока весь процесс находился в одном скрипте, такие ошибки приходилось исправлять уже по дороге к рендеру.

Поэтому сценарий — самостоятельная **граница данных**: здесь разрешена творческая генерация текста, но дальше передаётся только результат, прошедший правила выбранного `Recipe`. Такая архитектура позволяет заменить Gemini другим поставщиком, сохранив контракты следующих этапов.

**Возможная замена:** другая LLM или собственный генератор текстов. Это не готовая кнопка выбора любого провайдера — понадобится адаптер, который возвращает совместимый `Script`, и проверка его результатов.


## Задача

Получить не произвольный текст, а **структурированный сценарий**, который система сможет проверить и далее использовать без догадок о том, какая картинка относится к какой строке.

## Входные данные

- Выбранный **Recipe** (`alphabet` или `counting`).
- Каталог допустимых визуальных объектов (`Catalog`).
- Настройки сценария, включая seed.
- Параметры выбранного текстового провайдера.

Для Alphabet Recipe заранее известны требуемые буквы. Для Counting — числа и требования к числу изображений.

## Что происходит

`Recipe.script_prompt()` формирует задание для текстовой модели и передаёт описания разрешённых ассетов. Текущий live-адаптер `GeminiText` возвращает структурированный результат по схеме `Script`.

`Recipe.validate_script()` проверяет смысловые ограничения. Для Alphabet, например, каждое тело сцены должно начинаться конструкцией вроде `A is for ...` и соответствовать имени/алиасу объекта с нужной буквой. Сегменты `INTRO` и `OUTRO` подчиняются отдельным правилам.

**Контроль соответствия не делегирован полностью LLM.** Даже если ответ выглядит правдоподобно, правила Recipe могут его отклонить.

## Выход

Объект `Script`: заголовок и упорядоченный список `Segment`. У сегмента есть ID, текст, при необходимости `asset_id` и подсказка аудиосекции. В job сохраняется `script.json`.

Фрагмент концептуального примера:

```json
{
  "id": "A",
  "text": "A is for Apple, ...",
  "asset_id": "a_apple_example",
  "audio_section": "verse"
}
```

`a_apple_example` здесь — **условный ID**; в реальном сценарии он обязан присутствовать в твоём manifest.

## Что можно заменить

- **Текстовую модель.** Сделать новый `TextProvider`, который возвращает совместимую Pydantic-модель.
- **Тему или формат.** Написать новый `Recipe` со своими сегментами, промптом и проверками.
- **Источник сценария.** Добавить программный или иной адаптер, который выдаёт тот же контракт.

Это **возможности расширения**, не готовые переключатели на произвольную LLM в конфиге.

## Где это в коде

- `src/genmedia/recipes/alphabet.py` — правила алфавита.
- `src/genmedia/recipes/counting.py` — правила счёта.
- `src/genmedia/recipes/_song.py` — общие правила песенных сценариев.
- `src/genmedia/providers/gemini.py` — обращение к Gemini.
- `src/genmedia/models.py` — `Script`, `Segment`.
- `src/genmedia/pipeline/orchestrator.py` — запуск, проверка и сохранение.

## Ограничения

Валидация сценария **не гарантирует**, что музыкальная модель потом правильно пропоёт каждое слово. Этот вопрос частично контролируется отдельным этапом синхронизации, но акустическое распознавание как независимая проверка в проекте не реализовано.
